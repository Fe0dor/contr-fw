## 1. P1 — UART молча превращает повреждённую команду в допустимую

**Место:** `hal/target/console.c:20–27`.

При заполненном приёмном кольце обработчик молча отбрасывает байты без уведомления ядра и без отбрасывания остатка текущей строки. Аналогично ORE/FE/NE лишь очищаются. Защита от переполнения в core/core.c не помогает, если байты уже потеряны нижним слоем.

**Доказательство:** `uart_repro.c` непосредственно включает неизменённый target/console.c; заменены только MMIO и вспомогательные функции и переименованы экспортируемые функции консоли, чтобы связать тест с актуальной host-библиотекой core. В UART до чтения переданы 499 LF и `ROUT:HIGH M4` (вместе 511 байт). Затем передан суффикс `,M5`, когда кольцо заполнено; после чтения кольца передан LF. Таким образом исходная непустая команда — `ROUT:HIGH M4,M5`, которая должна целиком отклоняться из-за interlock. Получено:

```text
UART before loss: head=0 tail=511
UART after loss: head=0 tail=511
UART command response -> OK
UART resulting relays -> M4
```

**Последствие:** включение выхода, которого не должно быть при недопустимой/повреждённой входной строке; молчаливая порча команд управления. Потери возникают при потоке быстрее обслуживания или длительной блокирующей операции.

**Подтверждено:** точная ветка переполнения target-драйвера и дальнейшее исполнение усечённой строки настоящим core. **Не проверено на железе:** частота возникновения и реальные интервалы обслуживания UART. Для FE/NE/ORE есть аналогичный дефект по коду, но отдельная инъекция аппаратных ошибок не выполнялась. Нужна передача признака порчи/переполнения в parser и синхронизация до следующего LF, а не молчаливое продолжение.

## 2. P2 — повтор имени реле изменяет состояние вместо ERR:RANGE

**Место:** `core/relays.c:68–73`.

В списке аргументов не проверяются уже встреченные имена, bit_set молча сворачивает повторы. FW-110 явно относит «повтор имени в одном списке» к ERR:RANGE без изменения состояния.

**Доказательство:** на свежем устройстве `ROUT:HIGH M4,m4` → `OK`; `ROUT:STAT?` → `M4`. Это воспроизводится в uart_repro.c до UART-сценария. Сравнение должно быть без учёта регистра. Существующий tests/host/test_relays.c также ожидает OK на повтор; это тест, противоречащий данному ТЗ.

**Последствие:** ошибочный список реле принимается и включает выход; аналогичная проблема в HIGH/LOW/SET. **Подтверждено:** командный сценарий на актуальном core. Гипотез об аппаратном поведении для вывода не требуется.

## 3. P2 — CFG навсегда теряет возможность записи после заполнения

**Место:** `core/cfg.c`, функция cfg_compact (строки 197–202; возвращает -2 без действий), связанное write_record и проверка cfg_free_records в core/update.c.

А10 и этап 2 предусматривают уплотнение заполненного CFG. Сейчас выделено 256 записей, а cfg_compact всегда отказывает. После заполнения ни SAFE, ни перезапуск не восстанавливают возможность изменить сеть; COMMIT с менее чем двумя свободными записями также отказывает. Повторные записи одинаковой сети тоже расходуют слоты.

**Доказательство:** cfg_repro.c записывает 256 допустимых CFG_NET, затем получает `free=0; new net write=-2; compact=-2`. Нынешний test_cfg намеренно фиксирует такое поведение. Это видимое ограничение реализованного этапа 2, а не отсутствие модуля будущего этапа.

**Последствие:** исчерпаемый ресурс для настройки сети и обновления; требуется внешнее вмешательство либо заранее выполненное успешное обновление, переносящее компактный snapshot в другой банк.

**Подтверждено:** заполнение и постоянный отказ записи на host flash-модели, ветка отказа COMMIT по коду. **Не проверено:** физическое заполнение flash. Комментарий о небезопасности односекторного стирания обоснован: исправление не должно просто вернуть erase старого сектора. Требуется отдельный устойчивый к потере питания протокол переноса/восстановления CFG; это более широкая работа, чем исправление обработки ошибки ниже.

## 4. P2 — USER сообщает сброс сети и перезапускает плату, даже когда запись не выполнена

**Место:** `core/netcfg.c:154–159`.

Возврат cfg_set_net проигнорирован. При заполнении CFG или ином отказе flash удержание USER 5 секунд пишет в журнал «net defaults, reset» и перезапускает плату со старыми настройками. Это отдельный дефект обработки отказа; возможен независимо от выбранного способа компактации.

**Доказательство:** cfg_repro.c после заполнения CFG удерживает модель кнопки 5000 мс, заново инициализирует core с сохранённым flash:

```text
full CFG: free=0; new net write=-2; compact=-2
USER 5s: reset=1; stored IP=0a141e28; expected default=c0a80014
after reboot NET -> static,02:D8:E9:ED:ED:49,10.20.30.40,UP
cfg_repro: OK
```

**Последствие:** штатная процедура восстановления доступа FW-229 не выполняется; пользователь ожидает 192.168.0.20, но адрес остаётся старым. **Подтверждено:** воспроизведение в host flash/button-модели и прямое игнорирование кода ошибки. **Не проверено:** отказ записи на физической плате. Локальное исправление — проверять результат и не заявлять успешный сброс/не перезапускаться со старыми настройками; полноценное выполнение FW-229 при полном CFG требует решения из пункта 3.
