# Независимое первоначальное ревью Astra: contr-fw

Дата: 2026-09-21. Проверен входной рабочий снимок на HEAD `27757a44dec8ab97fd949e031d9bc77830caa5db`, сохранённый основным агентом в `baseline/`. Точный незакоммиченный снимок прошлого Astra-ревью отсутствует, поэтому выводы относятся к расширенному diff HEAD, а не к доказанному diff между двумя ревью. Предыдущие отчёты ревью не читались. Исходники не изменялись. Реальная плата, UART и J-Link не использовались.

## Подтверждённые замечания

### 1. P1 — новый UART recovery удаляет уже принятую команду SAFE

Место: `hal/target/console.c:22` (очистка `rx.head = rx.tail` в `rx_reject`), вызов при overflow на строках 39–41. Также относится к очистке после UART error на строках 33–35.

После заполнения 512-байтового UART ring ISR удаляет всю очередь, включая ранее полностью принятую неповреждённую строку SAFE. Спасение SAFE в `core/core.c` не помогает: до этого кольца данные не доходят. В старом ISR на HEAD новые байты при заполнении отбрасывались, поэтому SAFE в начале очереди сохранялась.

Воспроизведение `repro_uart_safe_overflow.c` включает именно текущий `hal/target/console.c` под mock UART-регистрами, затем использует актуальные host core/hal библиотеки. Включается исключительно виртуальный HLG. В USART3 ISR отправляются `SAFE\n`, затем 100 строк `*IDN?\n` без промежуточного чтения. После чтения UART и 700 проходов суперцикла:

```
SAFE seq before=0 after=0; HLG on=1
uart_safe_overflow: 2 failure(s)
```

Ожидается принятый SAFE и HLG OFF. Ошибка позволяет оставить выход включённым после поступившего аварийного запроса при переполнении/ошибке UART. При 115200 baud 511 байт накапливаются примерно за 44 мс; синхронная работа firmware/flash может создавать окно без drain. Тесты host overflow не ловят это, поскольку минуют target UART ring.

Исправление должно сохранять завершённые достоверные SAFE отдельно от разрушаемой очереди и отдавать их главному контексту, без исполнения core-логики из ISR. Одного сохранения старого кольца недостаточно для SAFE после его переполнения. Подойдёт маленький независимый потоковый распознаватель только SAFE с учётом границ LF, ASCII whitespace/case и invalidation по NUL/FE/NE/ORE; отметка завершённой SAFE должна переживать последующий мусор. Повреждённую/незавершённую строку нельзя превращать в SAFE, и синтетический SAFE должен отделяться LF от неполного префикса core. Нужны случаи SAFE в начале, на границе и после overflow, валидный SAFE перед последующим UART error, отсутствие ложных SAFE из `SAFE junk`, NUL и разорванных повреждением `SA`/`FE`.

### 2. P2 — UI и эмулятор обновления сохранили старый контракт размещения образа

Места: новый контракт `core/update.c:365` и `hal/hal.h` (`HAL_IMAGE_MAX=768 KiB`); неприведённые потребители `emu/contr_emu/device.py:31,361,394–417`, `ui/contr_ui/workflows.py:56–59`, `ui/contr_ui/static/app.js` обработчик выбора firmware.

Firmware теперь требует маркер `CFG2` (`0x32474643`) и размер не более 768 KiB, поскольку сектор 10 стал транзакционным CFG backup. Эмулятор допускает прежние 896 KiB и совсем не проверяет маркер; валидатор UI также принимает старые образы. Это создаёт ложноположительный полный прогон обновления на эмуляторе и разрешает UI начать стирание/передачу legacy image, которое реальная firmware отклонит лишь при COMMIT.

`repro_model_contracts.py` создаёт 1024-байтовый образ с корректными header/vector/CRC, но legacy marker `0xffffffff`. UI его принимает, эмулятор получает `COMMIT -> OK`, состояние `COMMITTED`; `BEGIN 819200,...` тоже даёт `OK`. Независимый C harness `repro_firmware_contract.c`, связанный с актуальным core, показывает:

```
legacy BEGIN -> OK
legacy DATA -> OK
legacy COMMIT -> ERR:UPD_HEADER,layout
800KiB BEGIN -> ERR:RANGE,size
```

Нужно синхронизировать ограничение и marker в emulator, backend validator, frontend и генераторах тестовых образов. Добавить общие положительные и отрицательные примеры нового layout. Это не требование нового этапа: эмулятор/интерфейс уже обслуживают изменённый updater.

### 3. P2 — перезапуск эмулятора снимает внешние аварии БП

Место: `emu/contr_emu/device.py:176` — замена `self.psu` свежим `Psu` без переноса входных событий. `Psu.__init__` сбрасывает `alarm=False`, `dcok_mode='AUTO'`, `dac_fail=False`.

Удержанные кнопки DUT при MCU reboot явно сохраняются, но внешние условия PSU теряются. Reset CONTR не снимает ALARM внешнего БП и не восстанавливает DCOK/DAC hardware fault. Обновление/rollback вызывает этот reboot, поэтому тесты неисправности через перезапуск получают исправный стенд вместо сохранённой аварии.

Тот же `repro_model_contracts.py`: inject ALARM=1 и DCOK=0, затем `Device.reboot()` без отмены событий:

```
Before MCU reset: OFF,OFF,42,0,0,1
After MCU reset:  OFF,OFF,42,0,0,0
RSP enable with external ALARM still injected -> OK
```

Ожидается сохранённый ALARM и `ERR:PSU_ALARM`; output-состояние и программный fault latch можно и нужно заново инициализировать. Перенести внешние состояния модели в новый Psu и добавить тест reset/rollback с удержанным ALARM, принудительным DCOK и DAC_FAIL.

## Область проверки и ограничения

Прочитаны реализации CFG backup/generation/restore, dualbank update/boot, core queue/SAFE, PSU/DUT, target UART/GPIO/SPI, соответствующие модели и UI, ключевые host/Python тесты и применимые разделы ТЗ/плана. По CFG restore/commit/generation и сохранению trial counter дополнительных подтверждённых дефектов в этом проходе не найдено; это не является доказательством корректности при произвольных аналоговых повреждениях flash.

Прямые repro используют существующие актуальные host static libraries; полной параллельной сборки репозитория не было. Скрипты/бинарники и исходник старого ISR лежат рядом с отчётом. Основной агент отдельно сообщил о 69 PASS Python tests на входном снимке. Этапы 7+ и отложенные ручные измерения дефектами не считались.

Репозиторий не редактировался. Данные об аппаратной плате не использованы как подтверждение перечисленных дефектов.
