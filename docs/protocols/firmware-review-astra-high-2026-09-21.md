## Вывод

Обнаружен один блокирующий выпуск дефект P1: полная корректная команда SAFE может бесследно исчезнуть при переполнении входного кольца. Также подтверждено ограничение P2 журнала CFG, прямо отмеченное текущим кодом: после исчерпания журнала отсутствует восстановление его вместимости, перестают работать сброс сети кнопкой и последующие операции конфигурации/COMMIT.

## F1 — P1: переполнение TCP-кольца уничтожает уже принятую SAFE

**Место:** `core/core.c:66–77`, в особенности `c->head = c->tail` на строке 68. Связанные пути: `hal/target/net/net.c:on_recv` передаёт целый pbuf в `core_net_on_data` и подтверждает его `tcp_recved`; `check_pending_safe` выполняется только позднее, при `pump_channel`.

**Сценарий:** во время ожидания break-before-make команды `ROUT:HIGH M4` приходит один TCP-блок `SAFE\n` + 100 повторений `*IDN?\n`. Размер 605 байт, меньше обычного MSS 1460 и сконфигурированного TCP_WND 5840. Ни одна отдельная команда не превышает ограничения длины. Объединение нескольких команд в один сегмент допустимо для TCP; протокол отдельно требует ERR:BUSY для поступивших во время исполнения команд и исключение для SAFE.

**Причина:** при заполнении кольца на 511 байтах отбрасывается всё ещё не разобранное содержимое, включая полную первую SAFE. Остаток пакета разбирается как переполнение и запросы, но следов SAFE больше нет. Поздний look-ahead исправляет переполнение очереди строк, однако не может восстановить команду, уже удалённую уровнем кольца.

**Последствие:** текущая операция не прерывается, реле включается и остаётся включённым при живой TCP-сессии. SAFE не выполняется даже после полного опустошения очередей. Это нарушение FW-113 и FW-210, а не просто потеря ответа на остановку.

**Доказательство:** независимый `repro.c`, собранный в scratch с текущими `libcontr_core_mem.a` и `libcontr_hal_mem.a`; `repro.log`:

```text
inject 605-byte packet, SAFE first, during ROUT delay
ROUT reply: G1;OK
final SAFE sequence=1, generation=1, ROUT=G1;M4
desired nonempty=1
```

После входа клиента seq=1; SAFE должна была увеличить seq, прервать ROUT и погасить выходы. Тест прокрутил 200 циклов после приёма и опустошил ответы перед финальным запросом, поэтому это не задержка исполнения SAFE.

**Направление исправления:** сохранять уже завершённую SAFE независимо от переполнения очереди/кольца либо применять backpressure до подтверждения байтов TCP. Переполнение не должно превращаться в молчаливую потерю аварийной остановки. При этом запрещено распознавать SAFE из обрезанного или повреждённого префикса. Нужен отдельный регрессионный тест переполнения кольца, а не только LINE_QUEUE.

**Ограничение подтверждения:** опасное включение воспроизводилось только на host-модели. На аппаратуре используются исключительно OFF/read-only сценарии; приложение с HIL хранится отдельно.

## F2 — P2: при заполнении CFG перестают работать восстановление сети и дальнейшие записи

**Место:** `core/cfg.c:200–204`, `cfg_compact()` безусловно возвращает -2. Следствия: `write_record` не может дописать при CFG_RECORDS=256; `core/netcfg.c:162–167` не делает reset сети при ошибке записи; `core/update.c:cmd_upd_commit` отклоняет COMMIT при нехватке двух слотов.

**Сценарий:** после 256 корректных записей сети (возможны через повторный SYST:PROV:NET или USER reset; новый успешный update обычно уплотняет копию CFG и откладывает исчерпание) журнал заполнен. Удержание USER пять секунд при неверном статическом адресе уже не возвращает стандартную сеть. Перезапуск устройства не освобождает журнал, все его записи корректны. При одном свободном слоте COMMIT также уже не проходит.

**Доказательство:** `repro.c` заполнил текущую host flash-модель через публичный cfg_set_net, затем вызвал кнопку через host_set_button, elapsed BUTTON_RESET_HOLD_MS и обычный core_step:

```text
CFG free=0 compact=-2 nextwrite=-2
button reset_requested=0 error=UPD_SEQ,net defaults: CFG write failed
```

**Последствие:** восстановление адреса штатной кнопкой и обновление через Ethernet перестают быть доступными после достижения лимита; требуется внештатная работа с flash. Это относится к уже заявленному этапу 2: FW-229, А10/А11 и проверке уплотнения CFG в плане.

**Оговорка:** это явно документированное текущим кодом временное ограничение, а не незамеченная порча данных. Отказ безопаснее стирания единственной копии провижининга. Рекомендация — реализовать устойчивое резервирование/восстановление перед уплотнением, не возвращать прежнее стирание единственной копии. Если этап 2 сознательно принимается с этим ограничением, его следует явно записать как незакрытый пункт приёмки.

## Проверки и непревращённые в замечания гипотезы

- Все 12 существующих host-бинарников запущены напрямую: busy_queue, cfg, fuzz, netcfg, protocol, relay_table, relays, sections_ready, sections, start_order, target_uart, update — PASS. Запуск ctest в read-only проекте не мог создать LastTest.log; это ограничение sandbox, не отказ тестов.
- Проверены парсер/форматтер, очереди и арбитраж, SAFE, break-before-make, полные SR-образы, инициализация и восстановление секций, CFG, обновление/rollback, target GPIO/SPI/I2C/UART/ETH, linker и host fault-модели.
- Подтверждено, что BEGIN → ROUT:HIGH → DATA допускает запись flash уже вне in_safe_state. Отдельным дефектом не заявлено: FW-233 явно формулирует проверку для BEGIN, а запрет установок на всём промежутке обновления в ТЗ не определён. Желательно уточнить этот инвариант перед будущими силовыми этапами.
- Гипотеза tcp_close/ERR_ABRT проверена по vendored LwIP: текущий tcp_close_shutdown_fin превращает ERR_MEM в TF_CLOSEPEND+ERR_OK, поэтому предполагаемый обычный путь use-after-free не подтверждён и в замечания не включён.
- Не проверялись физические переходы реле, измерения осциллографом, ручное снятие питания/кабеля, SR0 loopback (петля не установлена), силовые выходы и будущие этапы.
